# أبواب تطمئن — منصة متابعة بثلاثة أدوار

هذه حزمة مصدر جاهزة **للإعداد والنشر** وليست موقعًا منشورًا بالفعل. لا يوجد رابط حي أو قاعدة بيانات متصلة حتى تكمل الإعداد.

**الشعار:** نتابع تقدّمهم… لتطمئن قلوبكم.

## الوظائف
- الطالب: 7 مراحل، 23 محاضرة (4–26)، علامتا مشاهدة وتدريب لكل محاضرة، 460 نقطة، مستويات وأوسمة.
- ولي الأمر: مشاهدة تقدم الطلاب المرتبطين به والتقارير المنشورة، دون تعديل علامات الإنجاز.
- المشرف: دعوات بريدية، ربط الطلاب بأولياء الأمور، لوحة إحصائية، نشر تقارير للأسر، وتحضير رسالة بريد عبر برنامج البريد الافتراضي.
- سمة داكنة/فاتحة؛ تصميم متجاوب؛ مزامنة بيانات عبر Supabase مع سياسات Row Level Security.

## إعداد Supabase
1. أنشئ مشروعًا جديدًا في https://supabase.com.
2. افتح SQL Editor ونفذ محتوى `schema.sql` مرة واحدة في **مشروع جديد**. راجع السياسات مع مسؤول حماية البيانات قبل استخدام بيانات حقيقية.
3. من Authentication > Providers فعّل Email؛ وفَعّل تأكيد البريد، واضبط Site URL وRedirect URLs على رابط موقعك النهائي. يُفضّل تعطيل التسجيل العام إن كنت ستستعمل دعوات Auth الإدارية بدل آلية التسجيل الموضحة أدناه؛ في الوضع الحالي يعمل التسجيل العام مع رفض الحسابات غير المدعوة بواسطة trigger.
4. **تهيئة أول مشرف:** قبل تسجيل المشرف، نفّذ في SQL Editor:
   ```sql
   insert into public.invitations(email,role) values ('admin@example.com','parent');
   ```
   استبدل البريد ببريد المشرف، ثم فعّل الحساب من صفحة الموقع بنفس البريد. بعد إنشاء الحساب نفّذ:
   ```sql
   update public.profiles set role='admin' where email='admin@example.com';
   ```
   هذه الخطوة تُجرى فقط من SQL Editor بحساب مالك قاعدة البيانات؛ لا توجد واجهة لترقية المستخدمين إلى مشرف.
5. افتح الموقع، أدخل Project URL و**publishable/anon key** فقط. تُحفظ الإعدادات محليًا في المتصفح؛ لا تستخدم `service_role` أو secret key إطلاقًا.
6. سجّل دخول المشرف، وأضف دعوات الطلاب وأولياء الأمور، ثم شارك رابط الموقع معهم. بعد إنشاء حساباتهم وربطهم، ستظهر بيانات الطالب للأهل.

**مهم:** البريد في جدول `invitations` هو سماح بالتسجيل، وليس إرسال دعوة تلقائيًا. بعد التسجيل قد يلزم تأكيد البريد الإلكتروني. التقرير المنشور يظهر في واجهة ولي الأمر المرتبط، وزر البريد يفتح رسالة `mailto:` ليقوم المشرف بإرسالها يدويًا؛ لا يوجد إرسال بريد آلي. تسجيل الطالب يتطلب بريدًا خاصًا به. لا تُنشئ حسابات الطلاب القاصرين دون موافقات المؤسسة والأسرة.

## نشر GitHub Pages
1. أنشئ مستودع GitHub خاصًا أو عامًا حسب سياسة مؤسستك، وارفع `index.html` و`app.js` و`.nojekyll` إليه في الجذر.
2. Settings > Pages > Build and deployment > Deploy from a branch، ثم اختر `main` و`/(root)` واحفظ.
3. افتح رابط Pages، أدخل URL ومفتاح Supabase العام، ثم سجّل الدخول.
4. في Supabase > Authentication > URL Configuration أضف عنوان GitHub Pages إلى Site URL/Redirect URLs.
5. تنبيه: **GitHub Pages قد يتطلب مستودعًا عامًا وفق خطة GitHub وإعدادات المؤسسة**؛ خصوصية بيانات الطلاب تعتمد على المصادقة وRLS، وليست على إخفاء ملفات الواجهة. لا تضع أسرارًا أو بيانات طلاب في المستودع.

## النسخ الاحتياطي والاختبار
- من Supabase استخدم النسخ الاحتياطية المتاحة في خطتك، أو `pg_dump` من بيئة موثوقة. لا تنشر نسخ قواعد البيانات على GitHub.
- اختبر بحسابات وهمية: مشرف، طالبان، وليا أمر؛ تأكد أن كل ولي أمر لا يرى إلا الطالب المرتبط، وأنه لا يستطيع تعديل تقدم الطالب.
- افحص قيود الخصوصية، الاحتفاظ بالبيانات، والموافقة قبل الاستخدام الفعلي.

## حدود النسخة
- لم يتم نشرها أو اختبار اتصال حي بقاعدة بيانات فعلية هنا؛ يلزم إعداد مشروع Supabase وربطه.
- التقرير لقطة عند النشر؛ لا يتغير تلقائيًا بعد تعديل إنجاز الطالب.
- لا يوجد توليد أسئلة بالذكاء الاصطناعي أو إرسال بريد آلي أو إدارة حذف الحسابات أو استعادة نسخة احتياطية من الواجهة.
- ملف `original.html` نسخة محفوظة من المصدر الأصلي للمقارنة ولا يلزم رفعه إلى الموقع.

## ما الجديد في هذه الحزمة؟
- تحديث العنوان والشعار الرئيسي والعبارات التعريفية والتحفيزية لواجهات الطالب والمشرف وولي الأمر.
- الاحتفاظ بزر الوضع الداكن والفاتح ونظام الصلاحيات والمتابعة والتقارير.
- ملف `original.html` محفوظ للرجوع فقط؛ **لا ترفعه إلى GitHub Pages**، لأنه ليس جزءًا من الموقع الحالي.
- لا يتضمن الموقع إرسال رسائل تلقائيًا؛ يتطلب إرسال البريد تأكيد المشرف من برنامج البريد.
